### 4.2 模块职责

| 模块 | 职责 | 关键约束 |
| --- | --- | --- |
| BrowserHost | 承载页面、管理 CDP 会话、转发注入脚本 | 不阻塞主线程；会话崩溃可重建 |
| RuleEngine | 纯函数式匹配 + 动作决策，输出“处置指令” | 单请求匹配 < 5ms；规则变更热生效 |
| RequestRouter | 执行处置指令（continue/rewrite/fulfill/fail/delay） | 与浏览器实现解耦，便于换方案 |
| CaptureService | 收敛 CDP 事件为统一事件模型，写入会话总线 | 可开关、可采样；大 body 不阻塞 |
| LogCollector | 增量读取、轮转、解析、建立时间/键索引 | 大文件不 OOM；10MB/s 级吞吐 |
| CodeIndexer | 文件树、搜索、符号、堆栈映射 | 增量索引；尊重 .gitignore |
| DiagnoseOrchestrator | 上下文打包、工具调用循环、结果结构化 | 发送前可预览；工具步数上限 |
| Storage | 工作区/规则/会话/事件持久化 | 单机文件化（DEMO 无数据库）；SQLite 仅为早期草案 |

### 4.3 关键数据流

> 以下为设计意图。DEMO 的实际实现是 **webRequest 三钩子按前缀改道 / 复用 dev server 代理**，
> 不经过 CDP `Fetch` 暂停与重放，详见 [08 §8.4](./08-DEMO实现现状.md)。

**流程一：请求被路由到本地后端**

```
页面发起 XHR
  → CDP Fetch.requestPaused(requestId, request)
  → RuleEngine.match(request) → {action: forward(target: 127.0.0.1:8080)}
  → RequestRouter: Fetch.continueRequest(requestId, url 改写 / header 注入)
  → 本地后端响应 → （如需改包）Fetch.requestPaused(response 阶段）
  → 放行 → 页面收到响应
  → CaptureService 记录（含命中的 ruleId、traceId）
```

**流程二：错误捕获与聚合**

```
页面报错（4xx/5xx / 网络错误 / console.error / uncaught）
  → CaptureService 生成 ErrorEvent
  → 关联同一 traceId / 同一时间窗内的请求
  → UI 时间线标记 + 提示“检测到 N 个异常”
```

**流程三：一次诊断**

```
用户描述问题 → 点击诊断
  → Orchestrator 取上下文：命中的请求、错误事件、日志窗口(±N 秒或 traceId)、堆栈映射源码
  → 组装 Prompt（系统约束 + 证据包）
  → LLM 工具循环（最多 K 步）：search_code / read_file / query_logs / inspect_request
  → 输出结构化结论（JSON）→ UI 渲染证据链与修复建议
  → 用户采纳/追问/反馈 → 会话落库
```

> **DEMO 实现**：上述编排在三种入口（CLI / WebUI / Desktop）间共用；实际顺序为
> 预检 → 驱动 fire 取请求/响应/时刻/标记 → 等日志落盘 → 组 prompt → agent 循环（≤ 24 轮）
> → DiagnosisResult → 脱敏报告。模型侧通过 Claude Agent SDK 拉起 Claude Code 子进程，
> 工具以 **进程内 MCP** 形式提供（只读日志与源码）；非确定性由 **硬闸门 + n=3 多次判定** 兜底，
> 界面记录「一致 / 不一致 / 判不了」并声明“一致不等于正确”。详见 [08 §8.7 / §8.9](./08-DEMO实现现状.md)。

### 4.4 内嵌浏览器与拦截方案选型

| 方案 | 请求/响应拦截能力 | 实现成本 | 主要风险 |
| --- | --- | --- | --- |
| **Electron WebContentsView + webContents.debugger（CDP）** | 强：Fetch 域可暂停/改写请求与响应，Network 域可拿全量元数据 | 中 | CDP 会话生命周期管理；body 获取需额外调用 |
| 独立本地代理（mitmproxy 类） | 强：对任意客户端生效 | 中高 | HTTPS 需证书信任；跨域/Cookie 域处理 |
| 浏览器扩展（declarativeNetRequest） | 中：声明式重定向，拿不到完整响应体 | 低 | 需安装扩展；能力受限 |
| 外置 Chrome + CDP 连接 | 强 | 低 | 非内嵌，体验割裂 |

**已确认（DEMO）**：桌面形态使用 **Electron + WebContentsView + CDP 捕获请求**；
路由控制不走 CDP 暂停改写，而是 **Electron `session.webRequest` 三条钩子按前缀改道**：

| 钩子 | 挂载 Origin | 职责 |
| --- | --- | --- |
| `onBeforeRequest` | 宿主 origin | 改写目标路由，走本地端口 |
| `onBeforeSendHeaders` | 本地 origin | 抓预检（OPTIONS）携带的头 |
| `onHeadersReceived` | 本机 origin | 补 CORS 响应头 |

“自建壳 + dev server 代理”为备用方案，可能被淘汰；CLI / Web 形态没有内嵌浏览器，
browser 场景改用 playwright-core + 无头 Edge。详见 [08 §8.3 ~ §8.6](./08-DEMO实现现状.md)。

> 设计要点：CDP Fetch.continueRequest 做 URL 改写时，页面感知的 Origin 不变，可规避 CORS 问题；但 Set-Cookie 的 Domain 可能与本地后端不一致，需要单独的 Cookie 策略（P1 阶段处理）。

### 4.5 规则引擎设计（草案）

```json
{
  "id": "rule-001",
  "name": "订单接口走本地",
  "enabled": true,
  "priority": 100,
  "match": {
    "methods": ["POST", "PUT"],
    "urlPattern": "https://api.example.com/api/order/**",
    "resourceTypes": ["xhr", "fetch"],
    "headerConditions": [{ "name": "x-env", "op": "eq", "value": "prod" }]
  },
  "action": {
    "type": "forward",
    "target": "http://127.0.0.1:8080",
    "pathRewrite": { "from": "^/api/order", "to": "/order" },
    "headers": { "set": { "X-DebugCopilot": "1" }, "remove": ["Cookie"] },
    "timeoutMs": 30000
  },
  "injectTraceHeader": true
}
```

- **动作类型**：forward（转发）、mock（本地响应）、abort（中断）、delay（延迟）、patch（改包：JSONPath 或脚本表达式）。
- **匹配优先级**：priority 降序 → 同优先级按创建时间 → 首个命中生效（first-match wins）；命中后在 UI 中明确展示“被哪条规则处理”。
- **冲突与调试**：规则变更热生效；提供“为什么没命中”的诊断（逐条件求值结果）。
- **trace 关联**：命中请求可注入 X-DebugCopilot-Trace-Id（或复用后端已有的 trace header 名），用于日志关联。

> 规则 DSL 的完整字段、脚本沙箱能力与匹配语义详见后续同步（§11 T2）。

### 4.6 日志采集设计（草案）

- **增量读**：记录 fileId + offset，定时轮询文件大小；检测截断/轮转后重置偏移。
- **多行合并**：以“新行是否匹配起始模式（时间戳/级别）”为界，将堆栈行归并到上一条。
- **解析产物**：{ ts, level, logger, thread, traceId, message, stack, raw }。
- **索引**：按时间排序的环形缓冲 + 关键字倒排（内存）；超出阈值的大文件外置到磁盘。
- **查询语义**：timeWindow、keyword、traceId、level >= WARN，返回行号与上下文行。
- **关联策略（三层）**：① 参数 marker（最优先）；② 时间窗 + 线程；③ 业务 ID（跨线程）。traceId 仅在目标确实写入时作为补充，**不作为主路径**；结论中标注关联方式与可信度。

> **DEMO 实现**：不使用 traceId，而是在请求 body 的“可回显、不参与业务”字段注入 `dcprobe<随机hex>`，
> agent 用 `get_logs({marker})` 子串匹配日志；无安全字段时不注入并在 prompt 中声明。
> 落盘等待为固定 sleep 1.2s（实测延迟约 150ms）。
> 日志读取为**纯读文件 + 流式 readline + iconv-lite(GBK)**，识别轮转与堆栈续行，解析用预设/regex，
> 自动探测要求 >60% 命中且全可解析；**每次调用全量线性扫，不建索引**。
> 该策略在 M1/M2 扩展为三层（marker / 时间窗+线程 / 业务 ID），详见 [08 §8.8 / §8.9](./08-DEMO实现现状.md)。

### 4.7 源码索引与堆栈映射（草案）

- **索引**：文件树 + ripgrep 搜索；tree-sitter 解析符号大纲（按语言逐步接入）。
- **堆栈映射启发式**：

| 语言 | 堆栈形态 | 映射规则 |
| --- | --- | --- |
| Java | com.foo.Bar.baz(Bar.java:42) | 包路径 → 目录，类名 → 文件名，行号直取 |
| Node | at fn (/abs/path/file.js:10:5) | 绝对路径直接命中；node_modules 降权 |
| Python | File "/abs/path/x.py", line 10 | 路径直接命中 |
| Go | main.handler(0x...) /path/x.go:42 +0x1a | 取 file:line |

- **脱敏**：发送源码片段前，按规则扫描并去除密钥类字符串。

### 4.8 诊断编排（草案）

**上下文包（Evidence Pack）**

```
symptom   : 用户描述、页面 URL、发生时间
http      : 相关请求/响应摘要（错误优先，含命中规则）
errors    : console error / uncaught 异常堆栈
logs      : 时间窗或 traceId 命中的日志片段（含关联方式说明）
code      : 堆栈帧映射到的源码片段（file:line + 前后文）
workspace : 技术栈、目录约定、可用工具说明
```

**工具集（LLM 可调用）**

| 工具 | 说明 | 限额 |
| --- | --- | --- |
| query_logs(timeWindow, keyword?, traceId?) | 检索日志 | 每次返回行数上限 |
| inspect_request(id) | 查看某个请求的完整信息 | — |
| search_code(pattern, glob?) | 全文搜索 | 结果数上限 |
| read_file(path, range) | 读取源码 | 单次字节上限 |
| git_log(path, limit) | 最近改动线索 | P2 |

**输出结构（JSON Schema 概要）**

```json
{
  "rootCause": "…",
  "confidence": 0.0,
  "evidence": [{ "type": "log|request|code", "ref": "…", "note": "…" }],
  "fixes": [{ "summary": "…", "root": "backend|frontend", "file": "相对路径", "search": "原文", "replace": "新内容", "risk": "low|medium|high", "verification": "…" }],
  "verification": ["复现步骤", "预期结果"],
  "needsMoreInfo": ["…"]
}
```

> 前端源码根约定（2026-11-04）：`frontendProjectRoot` 为主字段；`frontendSourceRoot` 可选，留空默认等于项目根。堆栈映射会依次尝试 URL 路径、去掉/补上 `src/`、basename 兜底；`read_source` / `search_source` 支持 `root=frontend`。
>
> 退出清理：`before-quit` 阻止立即退出，等待本工具启动的前端 dev server、代理和 UI server 停止（7s 超时兜底）；`process exit` 再同步杀一次子进程树，避免关闭窗口后前端继续运行。
>
> 历史追问：`dc:followup` 基于 run 的上一轮证据/结论/fixes 调用 Agent 的 `followUp`，保存 conversation 并替换 `result.agent`；如存在已应用修改则要求先撤销，避免丢失撤销入口。历史页按 conversation 渲染纯对话流，每条 assistant 消息保留当时的完整诊断与修复建议，但历史视图只读；`dc:followup:progress` 提供简化思考进度。
>
> 诊断进度：`dc:diagnose:progress` 发送粗粒度阶段（日志关联、源码读取、AI 分析、工具调用、修复预览、自检、完成）；工具调用通过 `createTools.onCall` 逐条上报，界面只展示中文动作标签，不暴露模型内部推理。
>
> 其他后端源码：`workspace.extraSourceRoots` 仅声明位置，默认不加入工具与修复根；诊断请求显式带 `allowExtraSources` 时，才把目录以 `extra-<n>` 授权给 `read_source/search_source` 和修复预览/应用。未授权时证据包只给出 id/label，Agent 应通过 needsMoreInfo 提示用户开启。
>
> 2a/2b/2c 实现（2026-11-04）：模型只输出 `search/replace` 结构化建议；应用侧校验路径与唯一匹配并生成只读 diff 预览。用户在界面上确认后，主进程按 runId + fixIndex 重新校验并原子写入，应用前备份原文件到 `runs/<runId>/backups/`，支持撤销；保留原文件换行符与权限位。应用后可运行工作区配置的验证命令（超时与输出上限、写入 verification log），成功时重启前端。模型本身始终没有写权限。capture 模式没有请求重放，验证通过后仍需用户重新操作并诊断新请求。

- **步数上限**：默认 6 次工具调用，超限后要求模型先给阶段性结论。
- **证据约束**：结论中的每条判断必须引用 evidence 中的 ref，UI 可点击跳转。
- **提示词与模型策略**：**【待补充 T4】**
