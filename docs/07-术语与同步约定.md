## 12. 术语表

| 术语 | 说明 |
| --- | --- |
| 工作区 | 一套项目配置：前端/后端地址、日志路径、源码路径 |
| 流量规则 | 匹配条件 + 处置动作，决定请求最终去往哪里、如何变形 |
| 处置指令 | RuleEngine 输出给 RequestRouter 的结构化命令（forward/mock/abort…） |
| 证据包 | 一次诊断发送给模型的上下文集合（请求/错误/日志/源码） |
| 证据链 | 结论中可回溯到具体证据条目的引用集合 |
| 追踪 ID | 用于关联浏览器请求与服务端日志的标识；DEMO 用 marker 实现 |
| 场景文件 | 声明“怎么走一遍页面/接口”的配置；browser 块含 path、match（URL 子串）、actions（click/fill） |
| 驱动 | 执行场景的执行器：browser（playwright-core + 无头 Edge）或 HTTP（method/path） |
| marker | `dcprobe<随机hex>`，注入可被日志回显但不参与业务的 body 字段，用于日志关联 |
| 硬闸门 | 不依赖模型、由代码保证的判定条件；agent 单次结论不能单靠自己通过 |
| n=3 判定 | 同一场景跑三次，记录一致/不一致/判不了；一致不等于正确 |
| DiagnosisResult | 诊断产物：元数据 + target + 请求/响应 + marker 披露 + 时间窗统计 + agent 段（结论 + 证据链） |
| 脱敏报告 | 对 DiagnosisResult 做白名单投影后渲染的对外报告，去掉绝对路径、头值、日志与源码原文 |
| 自建壳 | 用本地壳页面 + dev server 代理实现改道的备用方案，可能淘汰 |

## 附：文档同步约定

1. 每次同步方案细节时，按“最小变更”原则局部更新，并在 §0 变更记录追加一行。
2. 新增内容若尚无定论，先以 **【待补充】** 占位，并登记到 §11。
3. 章节编号保持稳定，便于引用；新增内容追加到对应章节末尾，避免大范围重排。
4. 待办技术问题统一收敛在 §11，不散落在正文中。
